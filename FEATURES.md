## 0. Core Principles

- [x] **User choice** — every automatic behavior has a manual override
  *Auto-gain vs. fixed gain, PTT vs. voice activation, every chain stage toggles independently. The three stages whose parameters were hardcoded — the gate's attack/hold/release, the de-esser's ratio and split frequency, and the low-pass filter, which had no UI at all — are now exposed ([`app.slint`](crates/gui/ui/app.slint), [`read_chain_config`](crates/gui/src/main.rs)).*
- [x] **Encrypted end to end, always** — X25519 + ChaCha20-Poly1305, no plaintext path ([`crates/crypto`](crates/crypto))
- [x] **Explain everything** — no feature ships without a one-sentence description in the UI
  *Every settings section and every DSP parameter carries a plain-language sentence behind a hoverable circled-i, through one shared [`HelpIcon`](crates/gui/ui/app.slint) component (41 call sites). The sentence is also the accessible label, so a screen reader reads it without hovering.*
- [x] **Your data is yours** — decryption is on-device; there is no server in the call path at all ([`crates/net/src/peer.rs`](crates/net/src/peer.rs))
- [x] **Lightweight** — native Rust + Slint, no browser engine ([`Cargo.toml`](Cargo.toml))
- [x] **No central server required** — calls are direct or through a relay anyone can run; a contact whose address changed is found again through a DHT of nodes anyone can run (`antiphon-relay --dht`, §4); first contact needs only an invite link. The app ships with no relay, bootstrap node or directory built in, so nothing depends on a project-run server

## 1. Audio Suite

### Cleanup stage

- [x] **Noise Gate** — threshold, attack, hold, release, all four exposed in the UI ([`stages/noise_gate.rs`](crates/audio/src/stages/noise_gate.rs))
- [x] **Live meter showing what's passing through the gate** — the gate reports its own attenuation through the same `Stage::gain_reduction_db` channel the compressor uses ([`noise_gate.rs`](crates/audio/src/stages/noise_gate.rs))
- [x] **Noise Suppression** ([`stages/neural_suppress.rs`](crates/audio/src/stages/neural_suppress.rs)) — the RNNoise model the spec names, through `nnnoiseless` (pure Rust, weights built in, no C toolchain), on by default and placed **before** the gate so the gate judges your voice rather than your fan. The strength slider blends the cleaned signal with the original, aligned to the model's one-frame lag (measured: 479–480 samples) so the blend doesn't comb-filter. Removes over 10 dB of steady hiss in the test, and unlike the old method also takes out sound that comes and goes. The model only runs at 48 kHz, so at other device rates it falls back to the previous spectral-subtraction suppressor ([`stages/noise_suppress.rs`](crates/audio/src/stages/noise_suppress.rs)), which is also a switch in the UI for anyone who prefers it. Adds 20 ms of mic latency
- [x] **Warning at high suppression strength** — shown next to the slider, and only once past the strength that actually causes it, with the reason: speech and background share frequencies, so removing more of one removes more of the other
- [x] **High-Pass Filter** — adjustable cutoff, default ~80 Hz ([`stages/biquad.rs`](crates/audio/src/stages/biquad.rs))
- [x] **Low-Pass Filter** — adjustable cutoff, now reachable from the UI ([`stages/biquad.rs`](crates/audio/src/stages/biquad.rs))
- [x] **Echo Cancellation** ([`echo_cancel.rs`](crates/audio/src/echo_cancel.rs)) — a real NLMS adaptive filter, not the ducking workaround: it removes the echo instead of hiding it, so it still works while *both* people are talking, which is when an echo is most disruptive. Three parts, all of which are needed — a filter alone does nothing: bulk **delay estimation** by envelope cross-correlation (the echo arrives hundreds of ms late, and a 21 ms filter can only cover the tail it spans), the **NLMS filter** itself, and **double-talk detection** so your own voice does not wreck a converged filter. It **survives device hot-swap without re-converging** — a new output device has a new buffer, but the room is the same, so the delay is re-searched and the filter kept. Reaches ~15 dB of echo removal on synthetic paths; the meter shows what it is actually achieving, since a canceller doing nothing looks identical to one that is working until somebody complains. **On by default**, as the spec asks, with the manual off switch for headphone users who want the least processing. A **residual suppressor** follows: it learns, while only the far end talks, how much echo the filter leaves behind (a distorting speaker leaves plenty) and turns that down to as little as -30 dB, ramped so it never clicks; while you talk your voice dominates and passes through (tested: >25 dB off a soft-clipped echo, your voice within 3 dB during double-talk). **Limit:** the suppressor is broadband, not per frequency, so the echo left during double-talk is not removed
- [x] **AEC survives device hot-swap without re-converging** — `device_changed()` drops the now-stale far-end history and re-searches the delay, but **keeps the learned filter**. Relearning would mean several seconds of audible echo every time somebody swapped headphones, and changing headphones does not change the room
- [x] **De-esser** — split-band, with threshold, ratio, split frequency, attack and release all exposed ([`stages/de_esser.rs`](crates/audio/src/stages/de_esser.rs))

### Utility

- [x] **Push-to-Talk** — held, not toggled ([`crates/app/src/ptt.rs`](crates/app/src/ptt.rs), [`state.rs`](crates/client/src/state.rs))
- [x] PTT default key **Caps Lock** — the default on a fresh install wherever it can be held (Windows, X11); Space on macOS and Wayland, where it cannot ([`caps_lock.rs`](crates/client/src/caps_lock.rs)). Existing configs keep the key they already have
- [x] **Caps Lock as a momentary key** ([`caps_lock.rs`](crates/client/src/caps_lock.rs)) — on Windows a `WH_KEYBOARD_LL` hook swallows Caps Lock while it is push-to-talk, so the lock never flips, and reports held/released itself; on X11 the key goes through and the lock is cleared again on release with `XkbLockModifiers`. Only while Caps Lock is the PTT key *and* PTT is the mode — otherwise the key is untouched. macOS (HID access) and Wayland (portal) are still refused at bind time with the reason
- [x] **Detect key-capture failure** ([`key_capture.rs`](crates/client/src/key_capture.rs)) — keys that can't work are refused *with the reason and an alternative*, and after binding, the app watches for the key actually arriving and warns if it never does. That's the exact failure the spec names: a binding that saves fine, never transmits, and gets blamed on the microphone
- [x] **Voice Activation** with sensitivity slider ([`va_threshold`](crates/client/src/config.rs))
- [x] Live meter showing the threshold against your actual voice ([`main.rs` meter timer](crates/gui/src/main.rs))
- [x] Any input rebindable via the config menu ([`on_capture_binding`](crates/gui/src/main.rs), Keybinds tab)
- [x] **PTT, mute and deafen each switchable between hold and toggle** — PTT latches on press when toggled; mute and deafen toggle by default and can each be switched to *hold* (muted / deafened only while the key is down), Settings > Keybinds
- [x] **PTT release delay slider**, 0-1000 ms, so the tail of your last word isn't cut off
- [x] **Mute** and **deafen**, each independently bindable ([`on_toggle_mute`, `on_toggle_deafen`](crates/gui/src/main.rs))
- [x] Global hotkeys work while the app is unfocused — `device_query` polling ([`state.rs`](crates/client/src/state.rs))
- [x] **Live Monitoring** — hear your own mic ([`monitor_sink`](crates/client/src/state.rs), `on_toggle_monitor`)
- [x] **Readout of how much delay you're adding** — buffer plus an estimate for the sound card, shown as approximate ([`monitor_added_latency_ms`](crates/client/src/state.rs)). Reporting only our own buffer would understate it, and cpal can't report device latency portably — so it says "about", which is the honest form
- [x] **Mic Test & Record Preview** — records five seconds, runs it through the full chain and plays it back, so you hear exactly what others hear ([`record_mic_test`](crates/client/src/state.rs)). Nothing is kept. The **live loopback** toggle stays alongside it
- [x] **Device Hot-Swap** — change mic or output mid-call without dropping ([`ActiveCall::swap_output`](crates/client/src/state.rs), `on_device_changed`)
- [x] **Plugin Host** — your own **LADSPA, LV2 and VST3** effects in the microphone chain, on Linux, Windows and macOS ([`crates/audio/src/plugins`](crates/audio/src/plugins)). Settings > Voice > *Plugins* finds what's installed in each format's usual folders (or `$LADSPA_PATH` / `$LV2_PATH` / `$VST3_PATH`), adds it to the chain with a slider or switch per parameter, turns it on or off, reorders and removes it; the list and every value are saved in the voice preset. Plugins run after the tone stages and before pitch shift and reverb, fed the mono microphone on every input and averaged back from their outputs, so stereo plugins work. LV2 bundles are read with a small Turtle parser of our own (no lilv); the host provides URID map/unmap, options, bounded block length and is-live, gives event ports an empty sequence, and doesn't offer a plugin that needs anything more. VST3 through the MIT-licensed SDK's bindings ([`vst3`](https://crates.io/crates/vst3)), with the host application object, separate or combined edit controllers, stereo-only plugins and saved parameter values delivered as parameter changes. Tested against a real gain plugin built in all three formats ([`crates/test-plugins`](crates/test-plugins)). A plugin that won't start says why and the chain runs without it; one that crashes takes the app with it, as in every in-process host. Plugin windows (custom GUIs) are not shown: parameters are edited as sliders. VST2 is not supported (its SDK is withdrawn)

### Receive side (per person)

- [x] **Per-User Volume** — a per-person trim and mute on top of the master level, saved against the contact so a quiet microphone stays fixed across calls. Applied live to the playback loop; muting is local and the other side is not told
- [x] **Per-User EQ** — three tone controls (bass 200 Hz, voice 1.5 kHz, treble 5 kHz) applied to *their* audio on your end only, remembered against the contact so a boomy or harsh microphone stays fixed for every future call. Deliberately not a per-contact parametric editor: the problem is "their mic sounds bad", which three knobs answer. Flat sliders run no processing at all rather than three biquads sitting at unity, and the chain carries no gain stage so it can't fight the volume trim next to it
- [x] **Ducking** — both kinds: in a group, whoever is loudest stays as is and everyone else is lowered by the configured amount, ramped so it doesn't click ([`mixer.rs`](crates/client/src/mixer.rs)); and the other side is lowered while your own microphone is open, which breaks the echo loop without headphones

## 2. Lost Audio Recovery

- [x] **Forward error correction** — voice is Opus, and each packet carries Opus's own in-band FEC copy of the one before it ([`net/src/voice.rs`](crates/net/src/voice.rs)); the receiver rebuilds a single lost packet from the next with no round trip and no added latency, and the jitter buffer reports it as `Recovered` rather than concealed. The FEC share follows the loss the other side reports. Frames from older builds (raw audio with a decimated 8-bit backup, [`net/src/fec.rs`](crates/net/src/fec.rs)) are still decoded
- [x] **Retransmit request** — for files (`FileMissing`) and now for audio (`AudioMissing`). The receiver asks only for gaps it is genuinely stuck behind, once each, and skips any gap a backup copy already covers ([`take_retransmit_requests`](crates/net/src/jitter.rs))
- [x] **Adaptive jitter buffer** — reorders and conceals, grows immediately on a concealment and shrinks after a run of clean deliveries, floored at 10 ms and capped at the configured ceiling ([`net/src/jitter.rs`](crates/net/src/jitter.rs))
- [x] **Replay** — live, a gap that nothing repaired in time is filled by repeating the last good frame ([`PopResult::Concealed`](crates/net/src/jitter.rs)); but the lost audio itself is still **recovered**: a resend or late packet for a concealed moment is kept rather than dropped ([`take_late`](crates/net/src/jitter.rs)) and written back over its stand-in in the encrypted replay ring ([`SealedRing::overwrite`](crates/client/src/sealed_ring.rs)), so the clip cut for that moment plays the real words

### Replay — user-facing

- [x] **Recovered audio played back to you** — the replay clip for a damaged moment carries the recovered audio (above), and plays automatically or on a tap per the replay mode below; the clip is cut 800 ms after the damage settles, which is longer than a resend takes. Separately, a bindable **"save the last N seconds to a .wav"** keeps the whole ring. **Limit:** primary connection only; group-call legs repair with FEC and concealment but keep no replay ring
- [x] **Replay modes: Off / Ask me / Auto-play** — when the network damages a moment badly enough to cut a replay clip, *Auto-play* replays it immediately, *Ask me* shows a "Replay it" button on the call screen, *Off* just keeps it in the history list. Small losses FEC repaired seamlessly are never offered, since there is nothing to replay
- [x] **Replay history panel** ([`replay_history.rs`](crates/client/src/replay_history.rs)) — the 1.5 s before and 0.8 s after each damaged moment, kept as up to 8 clips with a Play button each. A clip is cut *after* the damage settles rather than when it starts, because a sentence cut off at the moment it broke is not something you can make sense of; a burst of loss with a good frame in the middle is one clip, not three; and a single repaired frame is 20 ms FEC almost certainly fixed perfectly, so it gets no clip at all. The tail length is derived from the settle window rather than set separately — the two drifting apart would mean asking for audio that was never recorded. In memory only, cleared with the call: writing clips to disk would turn a repair aid into a call recording
- [x] **Catch-up playback** ([`audio/src/time_compress.rs`](crates/audio/src/time_compress.rs)) — after a stall the jitter buffer holds a backlog, and playing it at normal speed means you hear every word but stay permanently behind. Once the backlog passes what the buffer would hold anyway, playback speeds up in proportion to how far behind you are, capped at 1.15x — past that the rhythm of speech is audibly wrong and the fix is more noticeable than the problem. SOLA rather than resampling: resampling to 1.1x also raises the pitch about 160 cents. Speed 1.0 is a true passthrough, so a healthy call pays nothing
- [x] **User-configurable buffer window**, 10-60 s, shared with the running call so a change applies to audio already being buffered ([`replay_cap`](crates/client/src/state.rs)). Capped because the ring is uncompressed f32 in memory — ~192 KB a second, so an unbounded window would quietly cost a gigabyte
- [x] **Ephemeral by design, and says so** ([`sealed_ring.rs`](crates/client/src/sealed_ring.rs)) — the ring and the replay clips are **encrypted in RAM**: received audio is gathered into 20 ms blocks, each sealed with ChaCha20-Poly1305 the moment it fills, under a random key made for that call and never written anywhere ([`memory_seal.rs`](crates/crypto/src/memory_seal.rs)). Old blocks roll off the front, and ending the call drops the key, so a memory dump, swap file or crash report taken afterwards holds ciphertext. Only the block still filling (under 20 ms) is plaintext. Never written to disk unless you press Save. While the call runs the key is in the same process, which the help text says rather than overclaiming

## 3. Connection & Trust Model

### Who you connect to directly

- [x] **Known contacts → Direct P2P** ([`PeerConnection`](crates/net/src/peer.rs))
- [x] NAT traversal — STUN discovery plus UDP hole punching ([`stun.rs`](crates/net/src/stun.rs), [`PeerConnection::punch`](crates/net/src/peer.rs))
- [x] **Relay (default for everyone else)** — [`antiphon-relay`](crates/relay) pairs two sockets on a blinded token and forwards sealed frames byte for byte, so an unmodified `PeerConnection` aimed at the relay *is* the relayed call ([`net/src/relay.rs`](crates/net/src/relay.rs), real-socket test in [`relayed_call.rs`](crates/relay/tests/relayed_call.rs)). Self-hostable as a binary or Docker image; set in Settings > Call. A listener registers there, and invite links carry the relay plus a secret so a stranger can ring through it
- [x] **Anonymity mode** — multi-hop relay routing ([`net/src/onion.rs`](crates/net/src/onion.rs), [`relay/src/onion.rs`](crates/relay/src/onion.rs), [`anonymity.rs`](crates/client/src/anonymity.rs)). Settings > Call > Advanced takes two or three hop nodes (`antiphon-relay --hops`); relay dials and registrations then run over a circuit built in one round trip, with per-hop keys from an X25519 exchange against each hop's key, so the first hop sees you but not where you go and the target relay sees only the last hop. The call code is unchanged: a circuit is presented as a local socket. Automatic connection choice never goes direct while it is on, and the call shows **Connection: Anonymous**. Tested with a real handshake and audio through two hops plus a target relay. Data cells are the **same size on every link** (padded to one of a few sizes; each hop peels from the front and tops up with random filler, told its position in its sealed setup). Hop keys are **pinned**: `host:port#key` in the hop list, otherwise the first key a hop gives is remembered and a different one refused. A hop that doesn't know a circuit answers DESTROY, and the caller's shim **rebuilds the circuit** through the same hops on the same socket (also when it sends into a minute of silence); tested by restarting the exit mid-call. Settings > Privacy > Anonymity in the Stoop app. Group-call mesh legs and the SFU room connection go through the same circuit too, and hole punching between legs is refused while it is on. The cells that **build** a circuit are fixed-size too: every CREATE is padded to one length on every link (each hop's setup has a fixed size for its position and the hop tops up what it passes on with filler), and CREATED is framed like the smallest data cell
- [x] **Mode chosen automatically by contact status, overridable per conversation** ([`connection_mode.rs`](crates/client/src/connection_mode.rs)) — known contacts (a completed call or a verified key) go direct, everyone else through their relay; each contact row has Auto / Direct / Relay. With no relay to use, an automatic relay call is **refused with the reason** rather than quietly placed direct, since that would expose both IP addresses without saying so
- [x] **Active mode visible in the call UI with a one-line explanation** — "Connection: Direct" (you can each see the other's IP address) or "Connection: Relayed" (neither of you can, and the relay can't read or hear anything), decided from where the connection actually arrived rather than from what was asked for

### Group calls

- [x] **Up to ~5 people — direct mesh, no infrastructure** ([`group.rs`](crates/client/src/group.rs), [`mixer.rs`](crates/client/src/mixer.rs)) — during a call, a contact's Call button becomes Add. The person adding someone connects to them, then introduces them to every existing member, who connect to each other directly: through the adder's relay on a one-off token when there is one (so members who are strangers never see each other's IP), by hole punching when there isn't. Every newcomer must prove to be the identity named in the introduction, so a leaked token can't join a call, and blocked people are refused. A mixer advances by the slowest *talking* person so two voices overlap instead of playing in turn. Covered by a three-person test that closes the mesh through a real relay. **Not done:** if the person you first connected to hangs up, your side of the call ends with them
- [x] **Beyond that — SFU relay forwarding encrypted frames** ([`relay/src/sfu.rs`](crates/relay/src/sfu.rs), [`net/src/sfu.rs`](crates/net/src/sfu.rs), [`sfu_call.rs`](crates/client/src/sfu_call.rs)). Adding a sixth person moves the call to your relay's SFU: a fresh group secret goes to every member over the call's own end-to-end sessions, everyone joins a room named by a daily-rotating token derived from it, and each uploads once. Audio in the room is **SFrame under the call's MLS keys**, sealed once per frame, and a frame is only opened if its sender's MLS leaf belongs to the identity that announced its room tag; nobody sends in the room until MLS has keyed them in. People past the mesh are linked only to whoever added them, so MLS KeyPackages, Welcomes and Commits also travel through the room, addressed to one member and sealed under the room secret, keeping the lowest-linked-leaf committer rule consistent. Announcements (identity and name, signed by the identity) are sealed under the room secret, so the SFU sees a room token, random per-call member tags and sealed bytes, never a name or a key. Joins need a stateless cookie so spoofed joins can't aim a room's fan-out at someone; a seat can't be taken from a live member. Up to 50 people by default. Tested with eight members on a real socket, and six people keying in over MLS through the room and hearing each other as SFrame. SFU, circuit and probe sockets go through the VPN when voice does, so the kill switch covers them
- [x] **Community owners can self-host their own SFU** — `antiphon-relay --sfu` (with `--sfu-max-members`, `--sfu-max-rooms`, `--sfu-max-rooms-per-addr`) on the same port as the relay, mailbox and files; off by default, and the operator commitment printed at start-up covers it
- [x] **Project-hosted relays as fallback** ([`fallback_relay.rs`](crates/client/src/fallback_relay.rs)) — your relay first, then your own fallback list, then the project's; each is probed (a dial for a random token, which a live relay answers "not found") so a dead one is skipped before a call relies on it, and the first that answers is used for listening, invites and group calls. The project's list ships **empty by decision** (§12 Q2 below): no project-run relays, so nothing depends on machines nobody is paid to keep up
- [x] **Relays peer with each other** ([`relay/src/federation.rs`](crates/relay/src/federation.rs), [`net/src/federation.rs`](crates/net/src/federation.rs), [`crypto/src/federation.rs`](crates/crypto/src/federation.rs)) — `antiphon-relay --federate --peer host:port[#key]`, off by default. No registry or authority: relays are known by an X25519 key, learned from the operator, from gossip, or by asking, and a candidate becomes a peer only by completing a handshake that proves its key (ephemeral–ephemeral plus both static keys, per-direction keys, replay window). Someone registered at relay A is rung through relay B: B asks its peers with a hash of the token, a peer must answer with a MAC keyed by the token over B's fresh nonce and its own key (so a hostile relay can neither claim someone it doesn't hold nor learn a token it doesn't have), then B dials the token at A as an ordinary client and passes the sealed datagrams through. Candidates, peers, handshakes per second, lookups and bridges are capped; strangers' requests are padded so no answer is larger. Apps ask their relay who it peers with and keep those as fallbacks (`Config::mesh_relays`). Tested with two and three relays (the third learning the first by gossip), a forged proof, a replay, a spoofed hello and a wrong pinned key
- [x] **Reachable through a contact's relay** ([`fallback_relay.rs`](crates/client/src/fallback_relay.rs)) — with no relay of your own and no fallback answering, the app listens at a contact's relay, but only one whose owner switched on Settings > Relays & mailboxes > "Let contacts use my relay" (off by default, spec §8 server-side opt-in). The consent travels as `lend=1` in their invite link and in the hello at the start of every call; your invite and hello then name that relay, so your contacts ring you there. Settings shows which relay is in use and why

### Encryption

- [x] 1:1 forward secrecy — symmetric KDF ratchet, a fresh key per message ([`crates/crypto/src/ratchet.rs`](crates/crypto/src/ratchet.rs))
- [x] AEAD with AAD binding, replay rejection, tamper rejection ([`session.rs`](crates/crypto/src/session.rs))
- [x] Out-of-order UDP tolerated via a bounded skipped-key cache ([`ratchet.rs`](crates/crypto/src/ratchet.rs))
- [x] **Authenticated handshake** — interactive triple-DH binding the session to both long-term identities, so a session proves *who*, not just "whoever is at this address" ([`handshake.rs`](crates/crypto/src/handshake.rs))
- [x] **Double Ratchet** ([`session.rs`](crates/crypto/src/session.rs)) — symmetric KDF chains plus the DH ratchet step: each side brings in a fresh X25519 key and mixes it into a root key that seeds the next chains, so a stolen chain key stops working within seconds instead of lasting the call (post-compromise security, tested by stealing a session's state and showing it can't read traffic after the steps). Adapted for UDP: both handshake chains run from the first packet so either side can talk at once, a side steps every 250 messages (about five seconds of audio) once it has seen the other's newest key rather than on every reply, late packets from a finished chain still open from a bounded skipped-key store, and a forged header can't move the ratchet because nothing is committed until the packet authenticates. The handshake salt moved to v3 so an older build fails closed rather than exchanging frames neither side can read
- [x] **MLS (RFC 9420)** for groups ([`crates/crypto/src/group.rs`](crates/crypto/src/group.rs), on `openmls` 0.9.2) -- create a group, add and remove people by KeyPackage, join from a Welcome, apply commits, seal application messages, and export a per-epoch secret. A member's MLS credential *is* their Ed25519 identity key and every MLS signature is made by it, so a group member is the same verified person as a 1:1 contact; a KeyPackage or leaf that names one identity but signs with another is refused. **Group calls use it** ([`group_keys.rs`](crates/client/src/group_keys.rs)): once a third person joins, the members run MLS over the call's existing encrypted links (KeyPackage / Welcome / Commit control messages, split to fit a datagram). With no server to order commits, the member at the lowest leaf index among those still connected commits, so a committer who leaves is replaced by the same rule; someone who leaves is removed within a second, which is a new epoch; a member that misses a commit drops its group and rejoins. The call screen shows the current group key number. Tested with three members (add, add, remove, the removed one locked out of later messages and keys) and over a real three-person mesh through a relay. **Not done:** MLS state lives only as long as the call (group chats and communities, which would keep it, are not built yet); two people adding someone at the very moment a 1:1 call becomes a group would start two MLS groups, and the losing side's audio then stays on per-link encryption only
- [x] **SFrame** for media through a relay ([`crates/crypto/src/sframe.rs`](crates/crypto/src/sframe.rs)) -- RFC 9605 header, key derivation and the `AES_128_GCM_SHA256_128` suite, matching the RFC's Appendix C test vectors; keys from the MLS exporter per epoch, with each sender's KID carrying its leaf index so every sender has its own key and nonce space; a 128-frame replay window per sender, and a frame claiming a different sender than the stream it arrived on is refused. In a group call every member's audio is sealed once under the current epoch's key, and audio from a keyed member that arrives *without* SFrame is dropped. **Forwarded through a relay:** past five people the call moves to an SFU (§3 group calls above), which forwards SFrame frames it cannot read; the mesh still uploads one copy per person inside each link's session
- [~] **Multi-device** — **adding a device from an existing one is done** in both apps: Settings > Account & backup > *Send this account to a device* shows a link and QR code, and the new device (computer or phone) opens it on the same Wi-Fi and takes the whole account: identity, contacts, profile, settings and, if chosen, history ([`account_move.rs`](crates/net/src/account_move.rs)). The link carries a one-time key: the account is sealed under it, the new device must prove it holds it before anything is sent, it works once and closes after 10 minutes. Cross-signing is built too ([`device.rs`](crates/crypto/src/device.rs)): devices are signed into a sequenced list by the master key, revoked by omission. **Not done:** separate per-device keys in that list (today the devices share the account's key), and revoking one device from another
- [x] **Backup & recovery** — **account backup file**: Settings > Account & backup saves the whole account (identity, contacts, profile, settings, and message history if chosen) as one `.stoopbackup` file locked with a passphrase, and restores it on any computer or phone ([`account_backup.rs`](crates/client/src/account_backup.rs), [`account_seal.rs`](crates/crypto/src/account_seal.rs)). Argon2id (64 MiB, 3 passes, stored in the header so it can rise later) and ChaCha20-Poly1305 over the authenticated header; a file made on a phone restores on a computer and the other way round, contacts and profile translated, device-only settings kept. A restore moves the old account into a `replaced-<time>` folder instead of deleting it, then restarts. 24-word recovery phrase, shown in Settings > Account & backup on both apps (restoring takes the phrase or pasted Shamir shares) and restorable via `antiphon-cli identity restore` ([`mnemonic.rs`](crates/crypto/src/mnemonic.rs)), plus a backup key sealed per-device ([`backup.rs`](crates/crypto/src/backup.rs)) so restoring an identity and restoring history stay separate powers. **Shamir split** ([`shamir.rs`](crates/crypto/src/shamir.rs)): 2-of-3, 3-of-5 or 2-of-2 shares from Settings > Profile, or any split from `antiphon-cli identity split --need N --of M`, restored with `identity restore-shares`. Each share is a header plus 24 checksummed words, and a tag from the seed turns mixed or too-few shares into an error instead of a stranger's identity. Field arithmetic is bitwise, so timing doesn't follow the secret
- [x] **Persistent identity keys** — Ed25519 identity plus a signed X25519 prekey, generated on first run and stable across restarts ([`identity.rs`](crates/crypto/src/identity.rs), [`store.rs`](crates/crypto/src/store.rs))
- [x] **Identity is never server-scoped** — no address or host appears in an identity; where to reach someone is a separate signed record ([`route.rs`](crates/crypto/src/route.rs))
- [x] **Identity key storage** ([`keystore.rs`](crates/crypto/src/keystore.rs)) — on Windows the seed is sealed with DPAPI under the logged-in user, so the file is no longer readable bytes and neither another account nor a copy taken to another machine can unseal it. An existing plaintext file is upgraded in place the first time it is read, verified to keep the same identity. A sealed file that will not unseal is **refused, never replaced**: minting a fresh identity there would change who you are to every contact *and* throw away a key the recovery phrase could still have restored. The **backup key** — which decrypts every message you have ever sent — is sealed and migrated the same way ([`load_or_create_backup_key`](crates/client/src/history.rs)). On **macOS and Linux** the Keychain or the Secret Service (GNOME Keyring, KWallet) holds a random storage key and the file is sealed with ChaCha20-Poly1305 under it, through the pure-Rust `keyring` crate (no libdbus). Tested against a real GNOME Keyring over D-Bus. Only a definite "no entry" creates a new storage key; a locked or missing service falls back to the plain file rather than minting a key that would orphan every sealed file. A headless box with no Secret Service still writes plain, and says so. Sealing is user-scoped either way, so it stops another account but not code running as you

### What a relay operator can see — and the commitment

- [x] **Blinded session tokens, no persistent user identifiers at the relay** ([`relay_token.rs`](crates/crypto/src/relay_token.rs)) — pairwise tokens come from the static DH of both prekeys, so an operator cannot compute them even knowing both identities; invite tokens come from a secret only in the link. Both rotate daily, so the relay never sees a stable pseudonym
- [x] **No connection logs retained** — the relay has no logging at all; registrations expire after 60 s without a refresh and pairings 120 s after the last packet. `--stats-every` prints aggregate counts only
- [x] **The relay never holds a key to anything** — it forwards the same AEAD-sealed frames a direct call carries; the handshake runs end to end through it
- [x] **Stated publicly and plainly** — the operator commitment is printed at start-up, in `antiphon-relay --help`, and in the relay crate docs

## 4. Finding People (Discovery & Identity)

### Reaching people

- [x] **QR code / invite link** — `antiphon://<id>@<address>` links (links from before the rename, `voip://`, are still accepted), generated with a scannable QR ([`invite.rs`](crates/crypto/src/invite.rs), [`qr.rs`](crates/gui/src/qr.rs)) and pasted straight into contacts. Carries the permanent identity plus a bootstrap address, so first contact works with no directory, no relay and nobody listed anywhere
- [x] **QR reachable from the call screen** — as well as the profile settings page, it is a panel in the main view, toggled from the panel menu
- [x] **QR position user-configurable** — a full `FreeformPanel` like the others: drag by its title, resize from its corner, hide from the panel menu, saved per layout. **Off by default**, unlike every other panel: a code that identifies you should be on screen because you put it there, not because it happened to be on while somebody was sharing their screen. A layout saved before this panel existed loads with it hidden rather than dropped on top of an arrangement someone already made
- [x] Manual address exchange — add a contact by `host:port` ([`on_add_contact`](crates/gui/src/main.rs), [`Contact`](crates/client/src/config.rs))
- [x] Public address discovery, so you have something to share (`on_discover_public_address` → STUN)
- [x] **DHT** distributed lookup, so contacts find you after your IP changes ([`net/src/dht.rs`](crates/net/src/dht.rs), [`discovery.rs`](crates/client/src/discovery.rs)) — Kademlia over UDP, served by `antiphon-relay --dht`. With the DHT switched on (Settings > Call > Finding contacts, **off by default**, no bootstrap node built in) the app publishes where it is — public IP as a node saw it with the forwarded port, the STUN address, its relay and its signed route list — for today and tomorrow, again every 30 minutes and at once when any of that changes. It looks saved contacts up every 10 minutes and updates an address when a newer signed record says it moved; and when a direct call to a saved address gets no answer for 6 s, it looks that contact up on the spot, calls the new address, and then (in automatic mode) tries their relay. The app is a client only and never serves. Tested with twenty nodes on real sockets ([`dht_network.rs`](crates/net/tests/dht_network.rs)), through relays ([`dht_node.rs`](crates/relay/tests/dht_node.rs)), and end to end through the app's lookup into a saved contact
- [x] DHT records encrypted and signed ([`dht_record.rs`](crates/crypto/src/dht_record.rs)) — sealed under a key derived from the identity key and the day, so only someone who already has your identity key (a contact, or anyone you gave your link, which carries the same address) can read it; signed under a per-day **blinded** Ed25519 key (`A' = h·A`, as in Tor v3 onion services), so a storage node verifies the signature and refuses forgeries without learning whose record it is. A sequence number stops rollback: nodes keep only the highest per key and readers take only the highest, above what they already accepted
- [x] Blinded lookups, so nodes can't tell who you're searching for — records are filed and looked up under `H(A')`, which changes daily and can't be linked to the identity or to yesterday's key. A node that already knows your identity key could compute today's key and recognise lookups for you; one that doesn't, can't
- [x] Sybil / eclipse resistance *(spec makes this a hard requirement before DHT ships)* — after S/Kademlia: node ids are the hash of an Ed25519 key with a 16-bit proof of work, and every reply is signed by that key; a node enters a routing table only after answering a ping at the address it claimed; at most 2 nodes per /24 (IPv4) or /48 (IPv6) per bucket and 16 in the table; a full bucket keeps its old entry while it still answers; lookups run 3 disjoint paths that never share a node; storage is capped per node and per source network and expires after 48 h. Each mechanism has its own test. **Limit worth stating:** a 16-bit puzzle slows a Sybil attacker, it does not stop a well-funded one; the bucket diversity rules and disjoint paths are what make an eclipse need many networks, not many keys
- [x] **Opt-in directories** for public communities only — a node run with `--directory <file>` serves a listing of communities (name, description, link), paged and signed by the node's key; with `--directory-submissions <max>` it also takes **communities' own submissions**, each signed by its submitter, who alone can replace or withdraw it, at most five per network, kept in `<file>.submitted` for the operator to prune ([`dht.rs`](crates/net/src/dht.rs) `Request::Submit`). A community opts in under Moderation, "Open to people asking" (`listed` in its signed manifest), which gives it a **join link** carrying its host's route list ([`JoinLink`](crates/client/src/community.rs)); *List it* sends that to a directory. The app's *Find communities* (empty by default) browses only the directories you add, pins each one's key on first answer and refuses a listing signed by a different key, **searches within the listings** by every word typed, and **Ask to join** mails the host a request their app answers with an ordinary invitation, which you then accept or not. People are never listed
- [x] No global username search by default — there is no username search at all. The only lookups are a DHT lookup, which needs the identity key you are looking for, and community directories, which list communities (never people) and only from directories you added yourself

### Knowing it's really them

- [x] **Verification code** — a 40-digit code derived from both identities, shown in-call and printed by the CLI ([`verification.rs`](crates/crypto/src/verification.rs))
- [x] **Contact introduction** ([`introduction.rs`](crates/client/src/introduction.rs)) — the one discovery mechanism that needs no infrastructure: an existing encrypted channel *is* the transport. An introduced contact is recorded with its provenance and stays **unverified** — treating a friend's word as proof would let one compromised contact launder keys into everyone's address book, which is exactly what the verification code exists to catch. Self-introductions and re-introductions of blocked people are refused
- [x] **Trust-on-first-use** with a warning if a contact's key ever changes ([`contact.rs`](crates/crypto/src/contact.rs), `evaluate_peer_trust` in [`main.rs`](crates/gui/src/main.rs)). The key is pinned on first call, a change is surfaced loudly and **never re-pinned silently**, and only the user confirming a compared code accepts a new one
- [x] Friend requests ([`control.rs`](crates/client/src/control.rs)) ride an authenticated session, so they prove which identity sent them, and the contact now stores the peer's **identity key** alongside the address

### Infrastructure position

- [x] If project infrastructure disappears, existing contacts keep working *(true today by construction — there is none)*
- [x] Bootstrap nodes, fallback relays, optional directories — all three are `antiphon-relay` flags anyone can run (`--dht`, the relay itself with the app's fallback list in §3, `--directory`), and the app's lists for each start empty, so nothing depends on infrastructure the project runs

## 5. File Transfer

- [x] **Peer-to-peer by default, nothing uploaded to a server** ([`net/src/file_transfer.rs`](crates/net/src/file_transfer.rs), [`gui/src/file_transfer.rs`](crates/client/src/file_transfer.rs))
- [x] Offer / accept / reject flow ([`ControlMessage::FileOffer`](crates/client/src/control.rs))
- [x] Either side can cancel an in-progress transfer (`FileCancel`)
- [x] Chunked, whole transfer hash-verified end to end (SHA-256)
- [x] **Missing-chunk repair** — receiver lists gaps, sender resends just those (`FileMissing`). Each request is now **capped at 256 chunks** so it always fits in one 4 KB control datagram: before, a badly damaged transfer produced a request too large to send, so the transfers that most needed repair were the ones that never got it. While chunks are still arriving only true gaps are requested, not the tail the sender hasn't reached yet. Covered by a real-socket test that drops every third chunk and still gets the file byte-for-byte
- [x] Encrypted in transit — file frames ride the same AEAD session as audio ([`FrameType::File`](crates/protocol/src/frame.rs))
- [x] Progress UI ([`update_file_transfer_ui`](crates/gui/src/main.rs)) — progress, errors, **pause/resume**, and now two states that previously looked like hangs: *"checking it arrived intact"* while a large file is hash-verified, and *"resumed, N% was already here"* so a bar starting at 60% explains itself. In the iced desktop app, **a send queue**: pick several files at once and they go one after another, with each waiting file movable earlier or later, holdable and removable; files for someone else wait for your next call with them ([`transfer_queue.rs`](crates/client/src/transfer_queue.rs), shared with the phone). The queue **survives a restart** on both: it is saved as `send-queue.json` beside the app's data on every change, holds included, with a file cut short by the app closing put back first
- [x] **Content-addressed** — completed files stored under their SHA-256 ([`content_store.rs`](crates/client/src/content_store.rs)). An offer whose hash is already held skips the transfer entirely and goes straight to the save dialog
- [x] **Each chunk hashed and verified** — every chunk carries an 8-byte SHA-256 prefix of its own body, checked in [`parse_chunk`](crates/net/src/file_transfer.rs) before it is stored. A damaged chunk is rejected on arrival and re-requested by the ordinary missing-chunk path, instead of failing the whole-file hash at the very end with nothing to say which chunk was wrong. Eight bytes and not thirty-two because this catches *corruption*: forgery is already covered a layer down, since every chunk arrives inside the session AEAD. The whole-file hash is still checked at the end
- [x] **Transfers resume after disconnect** — the partial file on disk *is* the reassembly buffer ([`DiskReassembly`](crates/client/src/content_store.rs)), so resuming is just reopening it; there is no separate snapshot to keep in step. The index is saved every ~1 MB and data is flushed before the index, so a crash costs at most a megabyte of re-fetching and never an index claiming bytes that aren't there. Partials from earlier builds still resume. Cancelling your own download discards its partial; the *sender* cancelling keeps it, in case they offer it again
- [x] **Per-file key delivered inside the encrypted message**, so any peer can hold an unreadable copy ([`file_seal.rs`](crates/crypto/src/file_seal.rs)) — each shared file is sealed in 1 KB chunks with ChaCha20-Poly1305 under a key of its own, with the chunk index as nonce. The file's id is the hash of its size and every sealed chunk's hash, so a holder can check what it stores and serves *without* the key, and a downloader can reject a bad chunk the moment it arrives. The key and id travel in a `FileLink` message inside the call's encrypted channel ([`control.rs`](crates/client/src/control.rs)) and are kept in a shared-files list encrypted under the backup key ([`sharing.rs`](crates/client/src/sharing.rs)). The direct in-call transfer above is unchanged; the link is what makes the file fetchable afterwards
- [x] **Multi-peer download** — pull chunks from several peers at once ([`swarm.rs`](crates/client/src/swarm.rs)). One worker per holder that answers, all pulling from one shared queue, so a fast holder simply takes more chunks. The hash list is trusted only once it hashes to the id; a chunk that fails its hash or won't open goes back on the queue and a holder that fails three times in a row is dropped. Tested with two live holders and a dead address: the file arrives byte-for-byte and both holders served chunks. Holder protocol: [`blob.rs`](crates/net/src/blob.rs)
- [x] **No size limit** — streamed at both ends: the sender reads each chunk from disk as it goes ([`FileSource`](crates/client/src/file_integrity.rs)) and the receiver writes each one straight to its offset. Verified with a 64 MB transfer over real sockets. Hashing and verification stream too, and run on blocking threads so they never stall call audio. Streaming reopens a window the in-memory version didn't have — bytes are read after they were hashed — so every read checks the file's size and modified time and **stops with an explanation** if it changed, rather than sending content that doesn't match its own address. The receiver now confirms as soon as the file is verified and stored, not after the user picks a save location (which used to make the sender report failure if you took 20 s choosing a folder). Throughput is governed by the send-rate control in the next item
- [x] **Send-rate control** ([`pacer.rs`](crates/client/src/pacer.rs)) — AIMD pacing driven by the receiver's repair requests: slow-start until the first loss, then additive increase and a 30% cut on loss above a 2% noise floor, **at most one cut per 600 ms** — a burst is reported across several requests, and cutting for each report punished one event three times over. Repairs are served from the same paced loop as new chunks, so pause and the upload cap apply to them, and the receiver re-requests a chunk no more than once a second instead of repeating its whole list every round. Deadline-based rather than per-chunk sleeps, which also fixes the cap undershooting on Windows' coarse timers. Two receiver-side causes of loss found with the kernel's `RcvbufErrors` counter and fixed: the periodic index fsync ran inside the receive callback (now a blocking-thread job from a snapshot, same ordering guarantee), and the ~200 KB default socket buffer held fifty chunks (now 1 MB, `RECEIVE_BUFFER` in [`peer.rs`](crates/net/src/peer.rs)). The earlier "4 MB buffers made it worse" result was with the blast sender; with pacing in front, a bigger buffer is just fewer drops. **Measured, 64 MB over loopback, same machine:** before, 1.2 MB/s with 74 repair rounds and 1,160 datagrams dropped at the socket; after, 2.7 MB/s with 4 repair rounds and 47 dropped in a debug build, and **16.6 MB/s with 6 repair rounds in release** (previously ~1 MB/s in release, because the blast sender lost more the faster it went). The remaining debug-build ceiling is unoptimised decrypt per chunk, not loss

### Availability

- [x] **Seeding** — keep helping share a file after you download it, off by default. With it on, a file you send is sealed into a local store and served on its own port (3481); a file you download with the same key gets the same id, so it is re-seeded and joins the same swarm. Settings → Call → Shared files
- [x] **Seeding scope** — this conversation / this community / contacts / anyone, enforced at the protocol level ([`files.rs`](crates/relay/src/files.rs)). *Conversation*: the holder hands chunks only to whoever shows the file's read token, which is derived from the key. *Contacts*: also needs a signed, fresh claim from a saved contact's identity key, checked against the contact list at that moment. *This community*: the same signed claim, checked against the holder's copy of that community's signed member list at that moment, so a ban stops serving the banned member at once; a contact who isn't a member, or a member of a different community, is refused. A file shared in a community channel gets this scope unless your scope is *anyone*. *Anyone*: id only, still unreadable
- [x] **Anonymous seeding** through relays ([`sharing::route`](crates/client/src/sharing.rs), [`swarm::Route`](crates/client/src/swarm.rs)) — Settings → Call → Shared files → *Seed anonymously, through relays*, off by default. With it on, this device stops answering for files itself and its links carry no seeding port; instead every file you share or download is handed, sealed, to your pin nodes through an onion circuit over the hop nodes set for anonymity mode (`antiphon_net::onion`, one circuit per node), and the pin nodes do the seeding. Downloads and availability checks go through a circuit per holder too, so a holder sees only the last hop. A holder can still check the read token or a contact claim -- they prove permission, not location. With fewer than two hop nodes nothing is sent, rather than sent in the open. Tested over real loopback sockets with each node on its own address: the holder hears only from the exit hop, and a path that can't be built fails instead of going direct. **Limits:** the pin nodes see the files' sizes and when they arrive (never the contents), and timing between an entry and exit hop can still link the two ends, as with every low-latency onion route
- [x] **Pinning** — ask a device or server you trust to hold a copy. List pin nodes (and a community code if they ask for one) under Shared files; each file you share is uploaded to them sealed, chunk by chunk with every chunk checked against the id on arrival. Your uploads are filed under a per-node label (your signature over the node's name, hashed), so a node can enforce quotas without being able to link you across nodes
- [x] **Availability status** — *Available*, *Sender offline — will resume when they're back*, *No longer shared* ([`swarm::Availability`](crates/client/src/swarm.rs)). "Check availability" asks every holder of every listed file; a holder that removed a file says so instead of going quiet, which is what tells *no longer shared* apart from *offline*. A failed download re-checks and shows the state rather than an error

### Server-hosted mode (opt-in)

- [x] **Hosted file storage on the node** ([`files.rs`](crates/relay/src/files.rs)) — `antiphon-relay --files` accepts pinned uploads and serves them, on the same port as relaying and mail. Off by default; `--files-code` makes it members-only
- [x] **Per-community toggle, off by default** — *Server-hosted files* in a community's settings, signed into its manifest so only someone with Manage community can turn it on and every member sees the same answer. When on, a file shared in that community is also uploaded, sealed, to the file node the manifest names, with its `--files-code`; when off, only your own seeding and pin nodes hold it ([`share_in_community`](crates/client/src/sharing.rs))
- [x] **Max file size, total storage quota, per-user quota** — `--files-max-mb`, `--files-quota-gb`, `--files-per-user-mb`. Checked when an upload *starts*, from its declared size, so a node never takes half a file it can't finish
- [x] **Retention** — forever (default), `--files-expire-days N`, or `--files-expire-unopened-days N`, swept every minute
- [x] **Stored encrypted** — the node only ever receives sealed chunks and their hashes; the key never leaves the two people's devices
- [x] **Admin view of usage, manual purge** — a stats line every minute (files, bytes, served, refused), `--files-list` to print what's held, and `--files-purge <id|all>`. A purged file answers *no longer shared*, not silence

### Details that will bite if skipped

- [x] **Mobile file access** — a picked file is remembered by a handle that survives a restart, never a raw path: on Android a content URI with `takePersistableUriPermission` ([`AntiphonActivity.java`](crates/android/java/org/antiphon/app/AntiphonActivity.java), [`platform.rs`](crates/android/src/platform.rs)), on iOS a security-scoped bookmark resolved and opened on each read ([`crates/ios/src/platform.rs`](crates/ios/src/platform.rs)). Received files go to Downloads/Antiphon on Android 11+ and to the app's Documents (visible in Files) on iOS
- [x] **Moved or deleted files** — a file is read and hashed at the moment it is picked ([`file_integrity.rs`](crates/client/src/file_integrity.rs)), so anything already gone is reported before the offer rather than dying halfway with no explanation. Reading and hashing happen in one step on purpose: any gap between checking and reading is a window for the file to change, and with content addressing the hash *is* the file's identity
- [x] **Background transfers** — Android keeps calls, listening and transfers alive in a foreground service with Mute / Hang up in its notification ([`CallService.java`](crates/android/java/org/antiphon/app/CallService.java)); iOS has no such service, so it takes a `beginBackgroundTask` grace period and resumes the queue when the app is opened again. The shared app reports what is running through one call, `set_background_work` ([`platform.rs`](crates/mobile/src/platform.rs)). **Not done:** swiping the Android app away from Recents still ends a call, since the call lives on the activity's thread
- [x] **Thumbnails generated by the sender, sent inline** ([`file_preview.rs`](crates/client/src/file_preview.rs)) — a 64px PNG capped at 2 KB so it fits in the offer datagram. Sender-generated for the same reason link previews aren't fetched: a receiver rendering a preview is running an image decoder over a file it hasn't agreed to accept. The size limit and PNG magic are re-checked on arrival, since the sender chose those bytes
- [x] **Bandwidth controls** — an overall upload cap and an automatic throttle while a call is running, paced per chunk rather than in bursts ([`transfer_limits.rs`](crates/client/src/transfer_limits.rs)). Throttling during calls is *on by default*: an unthrottled transfer makes a call sound broken, and people blame the call rather than the file. A user's own lower cap is never raised by the in-call rule. Pause/resume as above. On the phone app: a one-at-a-time **transfer queue** (reorder, hold, remove), **only on Wi-Fi**, and a monthly mobile-data limit ([`queue.rs`](crates/mobile/src/queue.rs), [`files.rs`](crates/mobile/src/files.rs)). The iced desktop app now has the same queue (see Progress UI above)

## 6. Network Privacy Tools

- [x] **Bring your own VPN** — import a WireGuard configuration file ([`vpn/config.rs`](crates/net/src/vpn/config.rs), Settings > Call > VPN). Reads the wg-quick `.conf` every provider hands out: `[Interface]` PrivateKey, Address, DNS; `[Peer]` PublicKey, PresharedKey, Endpoint, AllowedIPs, PersistentKeepalive. Errors name the key to fix. `PostUp`/`PreUp` lines are shell commands for wg-quick to run as root, so they are ignored and **never run** — importing a file must not execute anything in it. One `[Peer]` per file: a provider's file names one server, and a mesh is a different product
- [x] **Userspace WireGuard inside the app**, not a system-level VPN ([`vpn/noise.rs`](crates/net/src/vpn/noise.rs), [`vpn/tunnel.rs`](crates/net/src/vpn/tunnel.rs)) — no TUN device, no admin prompt, nothing else on the machine changes. The tunnel is one UDP socket to the server; app datagrams are wrapped in IPv4/IPv6 + UDP headers with real checksums ([`vpn/packet.rs`](crates/net/src/vpn/packet.rs)) and encrypted. The protocol (Noise_IKpsk2 handshake, cookies/mac2, replay window, rekey and keepalive timers) is written to the whitepaper in pure Rust rather than taken from boringtun, because boringtun pulls in `ring`, whose C build breaks the Windows cross-build; interop was checked out of tree against boringtun 0.7.1 in both directions, with a preshared key, and through its cookie (under-load) path. Names are resolved through the config's `DNS` server inside the tunnel, so lookups don't leak to the local resolver either. Tested on real sockets: a client tunnel to a WireGuard "VPN server" on 127.0.0.1 that NATs to the destination, carrying both a bare datagram and a whole authenticated call handshake plus a voice frame
- [x] **Import, store, and switch between multiple configs** ([`vpn.rs`](crates/client/src/vpn.rs)) — the list is sealed under the backup key like history, in its own file; `config.json` holds only which one is active, so a settings export cannot carry a WireGuard private key, and the data export lists the file as deliberately omitted. Use / Delete per config, with endpoint, full-or-split tunnel and a key fingerprint shown — never the key
- [x] **Per-mode routing** — file transfers through the VPN while voice stays direct, or the reverse ([`vpn::Router`](crates/net/src/vpn/mod.rs), [`AppSocket`](crates/net/src/socket.rs)). Three switches: calls (the call socket and its STUN and relay traffic, group-call legs), shared files (swarm downloads, availability checks, pin uploads), offline messages (mailbox deposits and collection). Every socket for those is made by one router, so nothing that speaks a protocol needs to know about the VPN. Defaults when the VPN is turned on: files and messages through it, calls direct, since voice notices the detour first. Files sent *inside* a call ride the call's own connection and so follow the call's route: the other side, often behind a NAT, would drop chunks arriving from a different address. LAN mailbox discovery and the server roles (holding mail, seeding) stay direct — they answer whoever reaches this machine, which a tunnel without a forwarded port would make nobody. VPN off by default
- [x] **Key storage in the OS keystore** — DPAPI on Windows, Keychain on macOS, the Secret Service on Linux; see §6 above. Never in theme exports or backup blobs is already true and structural: the key lives in its own file, so settings export — which serializes `config.json` — cannot sweep it up
- [x] **Kill switch** — app traffic stops rather than falling back to your real connection. Off by default. With it on and the tunnel not running, a socket for a routed kind is refused (`NetError::KillSwitch`, shown where the call, download or message reports its error) and its DNS lookup too. Independent of the switch, a socket already inside the tunnel never falls back: when the tunnel stops, its sends and receives fail. Tested both ways, including that nothing reaches the destination after the tunnel drops
- [x] **Automatic port negotiation** ([`port_map.rs`](crates/net/src/port_map.rs)) — a NAT-PMP (RFC 6886) client, with the renewal loop that makes it mean anything: mappings expire by design, so a one-shot request would leave you reachable for an hour and then quietly not, with nothing on screen changing. Renewed at half the lifetime as the RFC prescribes, so a lost renewal still gets a second chance. An hour, not a day, so a hole left by a crash closes on its own. The **external port is read from the reply, never assumed** — routers are allowed to hand back a different number, and reporting the requested one would send people to a port nobody is listening on. Released when you switch it off and again on exit. Every refusal names a next step, because a failure the user cannot act on is noise. NAT-PMP only: UPnP-IGD is SOAP over HTTP with a long history of being exploitable, and the small protocol is the right one to add first
- [x] Handles port changes on reconnect without user action — the renewal loop keeps trying through a router reboot and picks the mapping back up, backing off so a router that is simply gone is not hammered. With the DHT on, a renewal that comes back with a *different* external port is followed ([`PortMapHandle::current_external_port`](crates/client/src/state.rs)) and the new address is republished at once (§4), so contacts find the new port without anyone re-sharing it. Without the DHT switched on, the mapping is still renewed but nobody is told the new port
- [x] **The port-forwarding capability table** ([`reachability.rs`](crates/client/src/reachability.rs)) — three rows in the Connect panel answering the questions people actually have: can I call out (always yes), is my public address known, and can anyone call me. The rule it turns on: **"not checked yet" is never reported as "no"** — one is a router to look at, the other is a button nobody pressed, and collapsing them sends people to debug a network that is fine. A refusal says what still works (call out, forward by hand, both press Punch) rather than overstating the problem
- [x] **Reachability status — always visible, never discovered through failure** ([`reachability.rs`](crates/client/src/reachability.rs), [`network_ui.rs`](crates/gui/src/network_ui.rs)) — the header always shows **Direct**, **Relayed — VPN doesn't allow incoming connections** or **Relayed — network blocks direct connections**, worked out at start-up from two STUN servers (a different public port per destination means a symmetric NAT, which can't be punched) and whether the default route is a VPN interface (routing table on Linux, `route` on macOS). With direct blocked and no relay answering it says so and points at Settings; hover explains, click re-checks. **Not done:** VPN detection on Windows (treated as no VPN)

## 8. Message Delivery

- [x] **Text chat, persisted** — encrypted over the control channel in call ([`ControlMessage::Chat`](crates/client/src/control.rs)) and stored per-identity, encrypted at rest under the backup key ([`history.rs`](crates/client/src/history.rs)), so a conversation reopens where it left off. Messages to someone offline go through the delivery routes below
- [x] **Outbox** ([`outbox.rs`](crates/client/src/outbox.rs)) — a per-contact queue, encrypted at rest under the same key as history, flushed the moment that contact is reachable again (including across restarts). A message leaves the queue **only when the transport confirms it went** — before this, `send_control`'s error was discarded and a message handed to a dying connection was shown in the sender's own log as though it arrived, which is the one failure a messaging app must not have. **Leave message** on any contact queues a message without a call; a background courier ([`delivery.rs`](crates/client/src/delivery.rs)) leaves it at their mailbox or sends it on the next call
- [x] **Multi-device catch-up** — *Hold mail for my other devices* runs a mailbox inside the app, open only to your own devices (the registration code comes from your seed). It reads what arrives there but leaves it in place, so your phone still collects it when it wakes
- [x] **Delivery Routes** — a single ordered list, walked top to bottom ([`delivery.rs`](crates/client/src/delivery.rs)). Your list is signed into a route record, sent to contacts in every `Hello`, and checked against their pinned key and sequence on arrival
- [x] Route 1: Direct — the only route that needs no infrastructure
- [x] Route 2: My other devices
- [x] Route 3: A node you trust — any `antiphon-relay --mailbox`
- [x] Route 4: Community node — the same node with `--mailbox-code`, joined with the community's code
- [x] Route 5: Project relay — the tier exists and works with any node address; it ships with no node in it, by decision (§12 Q2: no project-run relays)
- [x] Per-route on / off and reorder (Up / Down buttons rather than dragging)
- [x] Node picker — by address or node link, **Find nodes on my network** (broadcasts and lists every mailbox node that answers), and **Add by QR code**: a relay with a mailbox prints its `stoop://node/` link and QR code at start (`--announce host:port` names the address to put in it), and Stoop reads a picture of that code. A link with a members code goes on the community route, one without on the trusted-node route. Settings › Network › Mailboxes
- [x] Live per-node status: reachable, response time, messages waiting, storage used and the inbox cap, refreshed each courier round (every minute)
- [x] Remove or replace a node with waiting messages re-routed, not lost — senders keep a message in their outbox until a node accepts it, so a removed node only stops new deposits
- [x] **Redundancy setting** — first available vs. fan out; fan-out copies are dropped on arrival by sender and message id
- [x] **Strict mode** — publishes Direct only and stops this device leaving mail anywhere
- [x] **Per-contact route overrides** — *Mail: their routes* or *Mail: direct only* on each contact
- [x] **Server-side opt-in** — `antiphon-relay --mailbox`; off by default, and a node without it answers "doesn't hold mail" ([`relay/src/mailbox.rs`](crates/relay/src/mailbox.rs))
- [x] Operator controls: total and per-inbox storage caps, per-inbox deposits a minute, expiry in days, and own-community-only via a members code
- [x] Writes accepted only to labels registered with that node, so strangers can't fill a public node. Reading and deleting take a fetch secret the node holds only a hash of
- [x] Operator dashboard with no ability to see contents or identities — `--stats-every` prints inboxes, messages and bytes held, bandwidth and refusals; the node never has an identity or a plaintext to show
- [x] **The recipient's published route list decides where mail is deposited**, not the sender — the signed, sequenced record ([`route.rs`](crates/crypto/src/route.rs)) is published in every `Hello`, and senders deposit only at the nodes it lists, in its order. Labels are derived per node from your seed, so two nodes can't tell they hold mail for the same person; mail is sealed to your prekey with the sender's identity and signature inside ([`mail.rs`](crates/crypto/src/mail.rs)), so a node sees neither who sent it nor what it says
- [x] **Sender controls only the outbox** — a "keep trying" window from forever (the default) to 14 days, under Call → Undelivered messages. Forever by default because a message you meant to send is still one you meant to send a week later; when the window does run out, the messages dropped are reported rather than disappearing quietly. Where mail may be *deposited* stays the recipient's decision, not the sender's
- [x] **Delivery status wording** — the spec's exact three, shown against a message only while it is still queued: labelling every delivered line "Delivered" is noise, and noise is what stops people noticing the one that says otherwise. Three states and not two, because "sent" and "delivered" being one word is how an app claims something arrived when it only left

## 9. Chat & Communities

### Starting a call

- [x] Start a 1:1 call to a contact ([`on_start_call`, `on_call_contact`](crates/gui/src/main.rs))
- [x] Listen for an incoming call (`on_start_listen`, plus `server_mode` auto-listen)
- [x] Hang up, bindable to a key (`on_hang_up`, `hangup_key`)
- [x] **Silent call, including from the outset** — `Hello.wants_silent` carries the intent with the *first* thing sent, so the other end knows before it decides rather than being corrected afterwards; [`ControlMessage::SilentCall`](crates/client/src/control.rs) still turns a call already in progress into a knock. Both are *requests* that reach the one place that can only lower the receiver's outcome — there is deliberately no field or message that raises one. A greeting from a peer predating the field reads as "did not knock", since defaulting the other way would silence calls from anyone on an older build. Note that "ringing" today is a status line and a tray notification; there is no audible ring yet
- [x] **Shift+click, its own control, and an invertible default** — all three the spec asks for, with the priorities reversed. The visible "Knock instead of ringing" switch is always there; leaving it on *is* inverting the default. Shift+click on Call is opt-in (Settings → Call → Advanced) and **flips the switch for one call and puts it back**, so a modifier can never quietly change a standing preference. Shift+click is not the default here because a courtesy nobody can find is not a courtesy
- [x] **"Voice active · 3 people"** — on the call screen, and as a bar over a community's **voice channel** with everyone's names and Join / Leave ([`Space::voice_join`](crates/client/src/community.rs), [`engine.rs`](crates/desktop/src/engine.rs) `voice_room_upkeep`). A voice channel is a channel flagged `voice` in the manifest. Joining tells its readers you are there, with your invite link to be reached by, and repeats every two minutes; anyone not heard from for four and a half goes off the list, and word that waited in a mailbox is judged by when it was written. Of the people there, whoever has the lowest key puts the others through: they call the first, then add each one after to the call, so the group-call machinery (mesh, then the relay's SFU past five) does the rest, and if they leave the next lowest takes over. In the iced desktop app; not under a separate identity (the call is made with your main key, which would tie the two together)
- [x] **Escalate a silent call to a ringing one** — a "Ring them after all" button replaces Knock once you have knocked, sending [`ControlMessage::EscalateCall`](crates/client/src/control.rs). The connection, keys and audio all continue; only the notification decision is revisited. It withdraws the *caller's own* silencing and nothing more — the receiver's rules are re-read on their machine and still decide, so a contact set never to ring still does not. When their rules refuse, the caller is told, since an escalation that quietly did nothing would leave them waiting on an answer that is not coming
- [x] **Silent call in 1:1 as a knock** — its own button rather than a hidden Shift modifier, since a courtesy nobody can find is not a courtesy
- [x] **Receiver settings always win** — per-contact ring rules (always / silent only / never) plus a default and a do-not-disturb schedule ([`notify.rs`](crates/client/src/notify.rs)), and now **per-chat and per-community** rules, set in each group chat's or community's panel and kept on your device only. A saved contact's own rule wins; for a caller who isn't a contact, the rules of the spaces you share with them apply, the quietest one if several (a 1:1 call doesn't say which community it came "from", and *Never* on one must hold); then your default. *Never* on a space also mutes its message notices, while still counting unread
- [x] **A caller can never force a ring through do-not-disturb** — the decision is made on the receiving machine from the receiver's own settings, and every path through `notify::decide` either honours the rule or lowers the outcome. There is deliberately no input that raises it

### Communities

- [x] **Group chats up to ~100, no server required** ([`community.rs`](crates/client/src/community.rs)) — each is one MLS group ([`group.rs`](crates/crypto/src/group.rs)) plus a signed manifest of who should be in it, capped at 100. Messages go to each member over a live call's encrypted control channel when there is one, and otherwise sealed to them and left at the mailboxes *their* route list names (§8), cut into fragments that fit a mailbox and reassembled on arrival. Members learn each other's prekeys and routes from self-signed cards, so they need not be each other's contacts. Persisted across restarts — the MLS state, the manifest chain and every channel's history are encrypted under the backup key, as 1:1 history is. With no delivery service to order MLS commits, messages from a later epoch are held until the commit arrives, and two commits that cross in the mail are settled the same way everywhere (lower hash wins; the loser rolls back and redoes its change). Tested with three members through a real mailbox node on 127.0.0.1, and across a save and reload. Anyone in a group chat may invite one of their contacts; only its owners can remove people. Messages can be edited and deleted by their author. **Not done:** a member offline longer than the mailboxes keep mail misses a commit for good and is stuck until re-invited; nothing detects that for them
- [x] **Communities with channels, roles, permissions** ([`crypto/src/community.rs`](crates/crypto/src/community.rs)) — a community *is* its signed, versioned manifest: name, channels, roles with permission bits (manage community, channels, roles; invite, kick, ban, manage messages, post), members, owner keys, ban list and the nodes that serve it. Every change is a new version signed by its author, and every client accepts it only if the signer held, *under the version being replaced*, the permission for every change in it, and outranks anyone it affects — so a member can sign a "ban" but no one will accept it, and a moderator can't ban an admin or promote themselves. Starts with Admin / Moderator / Member. A community names its own mailbox, file and DHT nodes (`antiphon-relay --mailbox-code` / `--files-code`), and members can adopt its mailbox for their own mail in one click. Capped at 250 members without a board (5,000 with one) and one MLS group for all channels, so the channel isn't visible even to a mailbox. **Custom roles:** owners add, remove and rewrite roles (what each may do) from the Roles dialog, and anyone with "manage roles" gives members they outrank a role at or below their own; adding or removing a role renumbers the ones below it without moving anyone ([`Manifest::insert_role`/`remove_role`](crates/crypto/src/community.rs)). **Private channels:** a channel can list its readers in the manifest; posts, edits, deletes and files in it are sealed only to those readers and the owners, a receiver drops a private post from someone who isn't one, and members who can't read it don't see the channel at all ([`Space::send_in`](crates/client/src/community.rs)). They share the community's one MLS group, so a member removed from a private channel would still hold its keys if handed its ciphertext; nobody sends it to them. **Voice channels:** see "Voice active" above. **Full scale:** with a board, up to 5,000 members, see §11. A newcomer trusts the current manifest their inviter hands them rather than replaying its history — trust on first use, stated in the module
- [x] **Threads and replies** — any channel message opens a thread; replies carry the root's id inside the encrypted message and show as a count on the root, which opens the thread in place of the channel view
- [x] **Search over your own history**, indexed locally on your device ([`history.rs`](crates/client/src/history.rs)) — substring search over the current conversation, plus a per-contact Forget
- [x] **Moderation — block, mute, report, per-community ban lists** ([`moderation.rs`](crates/client/src/moderation.rs)). A block is keyed to the *identity*, so it follows the person rather than an address they can change, and it is enforced on the receiving machine before the call is shown — there is no server to do it. Reports stay on the device: nothing can read a call, so a report cannot carry evidence of one, and the UI says exactly that. Mute is per-contact (§1) and per-space (*Never* above). **Ban lists**: a ban is a signed manifest version adding the member to the ban list, with a reason, *and* an MLS commit removing them, so they cannot read anything sent afterwards (tested); every client refuses a ban from someone without the permission, refuses to re-add a banned key, and stops seeding that community's files to them. Moderators can also kick (removed, not banned), lift bans, and remove messages from members they outrank. In communities, a member can also **report messages to the moderators**: the excerpts go sealed only to them, never to the project. See §12 Q5 for slow mode, the flood cap and withdrawing invites
- [x] **Bots / API, local-first** ([`api.rs`](crates/desktop/src/api.rs), [`docs/local-api.md`](docs/local-api.md)) — a local API for your own scripts and bots: JSON lines on `127.0.0.1` only, port and a fresh random token in `api.json` (readable by your user alone), token first or the connection is closed. Commands do exactly what the app's buttons do — `me`, `contacts`, `messages`, `send`, `call`, `hangup`, `mute`, `door`, `status` — and `subscribe` streams incoming messages and call changes. Off by default (Settings > Privacy > *Scripts and bots*, or `--api`). A **bot** is the app run with no window as an identity of its own, `antiphon --profile mybot --headless`, plus any program speaking the API; an [echo bot](crates/desktop/examples/echo_bot.rs) is forty lines. Nothing is hosted anywhere

## 10. Platform Strategy

- [x] **Shared Rust core** — audio, crypto, net, protocol, and state split into separate crates ([`Cargo.toml`](Cargo.toml))
- [x] **Slint declarative UI** for desktop ([`crates/gui/ui/app.slint`](crates/gui/ui/app.slint))
- [x] Markup doubling as the theme format — the app is iced now, not Slint, so the theme format is Stoop's own Slint-style markup ([`markup.rs`](crates/ui/src/markup.rs)): one element of `name: value;` properties, with strings, colours, numbers, booleans, words and flat lists, and no expressions, bindings or imports. The built-in themes are markup files ([`crates/ui/themes`](crates/ui/themes)) compiled into the app, and exported theme files are the same markup; JSON theme files from earlier builds still load
- [~] **Desktop UI (Linux, Windows, macOS)** — one Slint UI. Builds, passes the full test suite and is clippy-clean on **Linux** and **Windows**; the [CI pipeline](.github/workflows/ci.yml) builds and tests all three on every push. The iced window has also been opened on **Linux** (under Xvfb): first-run welcome, adding a contact by address, and a real encrypted direct call between two instances with the verification card. **Not done:** the macOS GUI has been compiled and tested, not sat in front of; Linux was checked without a real sound card
- [~] **Mobile UI (Android, iOS)** — one iced app in Rust shared by both phones ([`crates/mobile`](crates/mobile)), not the Compose/SwiftUI-over-FFI the spec suggests, so a feature lands on both at once; each phone adds only a thin platform layer behind one [`Platform`](crates/mobile/src/platform.rs) trait. Screens: Call, Contacts, Chat, Files, Recent calls, Voice, Identity, Settings. Chat, history and file transfer *are* the desktop's modules, included by path, so a phone and a desktop exchange the same messages and files and write the same encrypted history. **Android** ([`crates/android`](crates/android)): a NativeActivity subclass plus a foreground service and a push receiver — four small Java classes, since a Service and activity results cannot be written in native code — built by [`build-apk.sh`](crates/android/build-apk.sh) instead of cargo-apk, which cannot package them. **iOS** ([`crates/ios`](crates/ios)): no Swift or Objective-C, Apple frameworks through `objc2`, CallKit for the call screen, built into an `.app` by [`build-app.sh`](crates/ios/build-app.sh) and in CI on macOS. Files stream from the phone 1 MB at a time through ranged reads of the picked document ([`stream.rs`](crates/mobile/src/stream.rs)), so there is no size cap; a file can be chosen for someone between calls and waits in a queue saved by its handle; an offer shows the sender's thumbnail. **Not done:** the Android app has run on a real phone, the iOS app only in CI builds -- it has not been run on an iPhone
- [x] **Audio backends** — `cpal` for WASAPI / CoreAudio / ALSA, with **PipeWire** preferred on Linux when its daemon runs and ALSA otherwise (`ANTIPHON_AUDIO_BACKEND=alsa` forces ALSA; the device lists and the stream that opens agree on the choice). On Android 9 and later a call opens **AAudio** directly ([`aaudio.rs`](crates/audio/src/aaudio.rs)) with the voice-communication input preset and usage, so the phone's own echo canceller and noise suppressor engage, plus `AcousticEchoCanceler` / `NoiseSuppressor` on the capture session; Android 8, or a stream AAudio refuses, falls back to cpal
- [x] **Push notifications** — **UnifiedPush** on Android (ntfy, or FCM as the distributor, so no Google SDK in the app) and **PushKit** VoIP pushes on iOS, which report a CallKit incoming call at once as iOS requires. Every push is one constant-size sealed blob ([`push.rs`](crates/crypto/src/push.rs)), so the push service learns that *a* wake-up happened and nothing about who sent it. A phone publishes where to wake it inside its signed route record, which contacts already check against its key. **Sending** ([`crates/push`](crates/push)): a desktop wakes a phone when a dial hasn't connected after 2 s and when it leaves mail for it, rate-limited per contact; a mailbox node (`--mailbox-push`) wakes a phone when mail arrives, and forwards a sender's sealed wake-up, which is how a desktop reaches an iPhone; **APNs** (ES256 token auth over HTTP/2) runs on a node built with `--features apns` and given an Apple key, since an app user cannot hold one. The **desktop persistent socket** is the open door itself: it listens, re-registers with its relay every 20 s and checks mail every minute. Design and what each party learns: [`docs/mobile-push.md`](docs/mobile-push.md). Phones keep no mailbox, so a message wake-up shows a notice rather than the message, and iOS gets call wake-ups only (no alert-push token yet)
- [x] **Packaging** — every release has Flatpak, AppImage, deb, APK, MSI and dmg, plus an NSIS installer and a plain tarball, all made by [`packaging/package.sh`](packaging/package.sh) from binaries that were built twice and compared. **Linux:** a single-file Flatpak bundle on the newest org.freedesktop.Platform ([manifest](packaging/linux/io.github.krifmaz.stoop.yml)), which CI installs and checks for any library the runtime lacks; an AppImage; a `.deb` whose Depends line comes from `dpkg-shlibdeps`. **Windows:** a per-user MSI built with WiX 4 ([`stoop.wxs`](packaging/windows/stoop.wxs)) for Group Policy, Intune or winget, and a per-user NSIS installer ([`stoop.nsi`](packaging/windows/stoop.nsi)) for people who download and run it; neither needs administrator rights. **macOS:** `Stoop.app` in a `.dmg`, signed ad hoc. **Android:** the APK from [`build-apk.sh`](crates/android/build-apk.sh). Not on Flathub or any store yet; that is a submission, not a build step
- [x] **One release pipeline building all targets from the same commit** ([`release.yml`](.github/workflows/release.yml)) — Actions → release → Run workflow builds Linux, Windows, macOS and Android from one commit, and every push to main does the same as a hotfix build. Every desktop binary **and the APK** is built twice from clean and compared byte for byte, and a release is refused if any differ; the files go out with `SHA256SUMS` and a signed build attestation each. The release does not wait for macOS, whose runners can be unavailable for hours: the `.dmg` is added to the same release when it is built. The iOS app is built from every commit by [`ci.yml`](.github/workflows/ci.yml); it is not a release file, since a phone installs only an app signed with an Apple developer account
- [x] Ship order — *decided: every platform ships together in every release* (Linux, Windows, macOS, Android, iOS from one commit, see the release pipeline above), rather than Linux + Android first

The node can't read the entries (sealed under a key from the MLS exporter of the epoch they were sent in, and signed by their poster), and doesn't know who the members are: access is by a per-epoch token it holds only as a hash, for the last 16 epochs, so a removed member is cut off without anyone telling it. **Manifest changes travel as deltas** (who left, who was added or changed, under the full version's signature), so a change stays small however long the member list is; a member who missed a version asks for it whole. A newcomer's Welcome, too big for mailboxes at that size, goes on the board, and they are mailed where it starts and the key for their epoch. Private channels and replies to one person still go member by member. *Full scale* in a community's settings (desktop and classic app) turns it on, on a mailbox node you name

## 12. Open Questions — still unanswered, and now load-bearing

1. [x] **Identity model** — usernames, keypairs only, or both? What's the recovery story when someone loses every device?
   *Answered in practice by what is built: identity is the keypair ([`identity.rs`](crates/crypto/src/identity.rs)), recoverable from a 24-word phrase ([`mnemonic.rs`](crates/crypto/src/mnemonic.rs)); the handshake is authenticated against it, which is what §4 verification, §3 cross-signing and authenticated friend requests rest on. The recovery story, in order: move the account from a device you still have (link or QR code); restore a passphrase-locked backup file, which brings contacts, profile and settings too; or, as the last resort, the 24-word phrase or Shamir shares, which bring back who you are so contacts still recognise you. No usernames: nothing here needs one, and a name registry would need the server this design does without. Someone who loses every device, every backup **and** the phrase starts again with a new key; nothing can be done for them, and the first-run flow says so by asking for a backup only after a real call*
2. [x] **Relay funding** — *decided: the project runs no default relays.* The fallback list ships empty ([`fallback_relay.rs`](crates/client/src/fallback_relay.rs)); people run their own (`antiphon-relay`, or the Docker image) and share them through invites, contacts lending their relay, and relay peering, so there is nothing for the project to fund
3. [x] **Push on iOS** — decided: the design in [`docs/mobile-push.md`](docs/mobile-push.md). Apple sees a fixed-size sealed blob under key `p`, VoIP pushes only for calls, so Apple learns timing but not who is calling; built on both ends (PushKit receiving, APNs sending from a node)
4. [x] **Federation** — can two self-hosted communities talk to each other, or are they islands?
   *Decided: not islands, at both layers. Relays peer (`--federate`, see §3), so a call or mail reaches someone registered at any relay in the mesh. Communities meet in **shared spaces** ([`community.rs`](crates/client/src/community.rs)): a space of its own whose signed manifest lists the communities (`alliance`) whose members may ask in, and which each of those communities lists (`allies`, changed only by whoever may manage it). An admin of community A starts one and gets a one-time `stoop://ally/` link (a ticket, good for a week) for an admin of community B; B's admin uses it to bring B in and becomes an owner of the shared space. After that any member of A or B asks in from their own community's list with a proof (their key there, signing the shared space and the key they ask with), sent to the member who listed it, who checks that key against their own copy of the community, so nobody has to trust the other community's servers or manifests. Inside, it is an ordinary community: channels, voice channels and calls, roles, moderation, all end-to-end encrypted and delivered by mailbox and peered relays like any other. Members never join the other community or see its channels; the shared space is the only thing in common. Stoop: the globe button on a community, **Shared with other communities***
5. [x] **Moderation without content access** — what are the actual tools, and what's the answer when a store reviewer asks?
   *Decided: moderation is done by the people who can already read the content, never by the project. The tools: blocking by identity (enforced on the receiving device), mute, per-community bans and kicks that also cut the person out of the MLS group, removing others' messages by rank, **withdrawing an invitation** (the inviter's app refuses that Join afterwards; unanswered ones run out after 14 days) and rotating your personal invite link, **slow mode** in the signed manifest (`slow_mode_secs`, set by whoever may change the community's settings) that every client holds its own posts to and drops others' posts that break, plus a **hard flood cap** of 10 posts in 10 seconds per member whatever slow mode says, judged on the time posts were written so mail delivered late isn't dropped, and **report to the moderators**: the reporter ticks messages, and the decrypted excerpts go sealed only to the owners and members who can remove messages or people, who see them in a Reports list marked against their own copy ("matches", "differs", "not in your copy") with Remove message, Remove member, Ban and Dismiss ([`community.rs`](crates/client/src/community.rs)). The store answer (Apple guideline 1.2 user-generated content, and Google Play's equivalent): content is end-to-end encrypted, so the developer cannot see or filter it; **reporting** goes to the community's own moderators, who act on it in the app; **blocking** is one tap and hides the person everywhere; **filtering** is the community's (bans, slow mode, flood cap, message removal); communities are invite-only and not listed unless their owners opt in; and the developer's contact address is in the listing for anything else. That is the same position as other end-to-end encrypted messengers: the moderation tools act where the content is readable, on members' devices. Check the guideline's current wording again before each submission*

- [x] **Reactions and soundboard** — **any emoji is a reaction**: four quick ones on every message and a picker with the rest, on the desktop and the phone, toggled by tapping, and **deleted with the message they point at** ([`reactions.rs`](crates/client/src/reactions.rs)): leaving thumbs-up under "(deleted)" would partly undo the deletion. What arrives from a peer is checked to be *one* emoji (a pictograph with its skin tone, a ZWJ family, a flag or a keycap, at most 48 bytes), or the reaction row becomes somewhere to put arbitrary text. In group chats and community channels, reactions are posts of their own (on/off, so a repeat delivery changes nothing), stored with the message, capped at 20 per member per message, and may be one of **the community's custom emoji** — accepted only if the community has that emoji, so a reaction never shows a picture the community didn't pick. That answers the earlier worry about rendering an image someone else chose: members are shown only what the people they joined under picked, never what any poster sends. Written `:name:` in a channel and drawn inline (large when a message is only emoji), picked from the composer's emoji button, managed from the community's channel list in the iced app
- [x] **Voice messages** — recorded through the same mic chain a call uses, silence-trimmed, capped at 2 minutes, and sent down the existing file-transfer path so they inherit its chunking, hash verification and repair ([`voice_message.rs`](crates/client/src/voice_message.rs)). The receiver is shown "Voice message", not a timestamped WAV. **Offline too** ([`voice_message::leave`](crates/client/src/voice_message.rs)): compressed with Opus to ~2 KB a second, pinned to your pin nodes, and its link sent through your message routes like a text; the receiver fetches and plays it, and a client that doesn't know the format still reads "Voice message (0:12)". In the iced desktop app, the composer's mic button records one (with a counter, Cancel and Send), and a received one shows as a player that fetches the clip as it comes on screen. **Not done:** recording on the phone
- [~] **Reproducible builds — configured, documented and checked** ([`BUILDING.md`](BUILDING.md)): single codegen unit, path remapping, `SOURCE_DATE_EPOCH` and `--locked`, with a table explaining what each one prevents. A `rust-toolchain.toml` was tried and removed — pinning a channel resolves against rustup's default *host triple*, which silently moved one machine from the GNU target to MSVC and broke linking; the toolchain is pinned per target in the pipeline instead, where the build matrix already knows its triple. **Proven on one machine:** two release builds of the same commit, with `cargo clean` between, produced byte-identical `antiphon` and `antiphon-cli` (hashes recorded in `BUILDING.md`). The release workflow repeats that cross-check on every release, for the APK too, and fails rather than publish a file that differs. **Signed:** every release file carries a Sigstore-signed build attestation, made by GitHub for the workflow run that built it, so `gh attestation verify <file> -R Krifmaz/Stoop` proves which commit and which run produced that exact file; the APK is also signed, as Android requires (with the release key when the `ANDROID_KEYSTORE_BASE64` secret is set, otherwise a throwaway one). **Not done, and said so:** the Windows and macOS binaries carry no Authenticode or Apple Developer ID signature, so SmartScreen and Gatekeeper still warn on first start; both need a paid certificate, which is the owner's decision. And both builds of the check run on the same kind of machine — a verifier matching the hash on their own is what closes that
- [x] **First-run experience** ([`first_run.rs`](crates/client/src/first_run.rs)) — the identity is generated silently before the first screen, and the opening message is *it already worked*, not homework. Backup is suggested only after a real call with a real contact, since asking someone to write down 24 words to protect an empty account teaches them prompts are noise. A test asserts the wording contains no jargon
- [x] **Data export in an open format** — settings, contacts, decrypted message history, soundboard clips and received files, written as plain JSON and WAV in a directory tree ([`data_export.rs`](crates/client/src/data_export.rs)). The identity and backup keys are deliberately excluded and the manifest says why, since a key in a folder people email around is how identities leak. The UI warns that the exported folder is unencrypted
- [x] **Mobile battery & data controls** ([`data_rules.rs`](crates/mobile/src/data_rules.rs), Settings in the phone app) — only-on-Wi-Fi transfers, a monthly mobile-data limit, a data saver that drops thumbnails, caps uploads and switches calls to Low data (8 kbit/s voice, no video) on mobile data, and whether to keep waiting for calls in the background and under battery saver. Turning background listening on asks for the battery-optimisation exemption, since Doze otherwise cuts the network minutes after the screen goes off. Each control carries its one-sentence explanation
- [x] **Crash reporting, opt-in only, no identifiers** ([`crash_report.rs`](crates/client/src/crash_report.rs)). Off means *nothing is written*, not written-and-withheld. Reports carry the panic message and source location with usernames, home directories, keys and addresses scrubbed, and the timestamp blunted to the hour so it can't be used as a correlation handle.
